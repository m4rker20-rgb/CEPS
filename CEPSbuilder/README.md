# CEPSbuilder

Защищённая упаковка плагинов exteraGram. Формат шифрования — **CEPS-1**
(аналогия: у Elyx есть ElyxBuilder → у нас CEPSbuilder и архивы `.ceps`).

## Что даёт CEPS-1

| Механизм | Что защищает |
|---|---|
| Подпись **Ed25519** | Никто не соберёт «обновление» от имени автора — приватный ключ только у него |
| **Цепочка блоков** сборок | Историю билдов нельзя переписать задним числом (каждый блок хеширует предыдущий, genesis = `0x00*32`) |
| **Merkle-дерево** файлов | Изменение любого байта любого файла ломает корень — детектируется |
| **ChaCha20** шифрование | Исходники не читаются «с коробки» ни в архиве, ни в лоадере |
| Прокси-класс в лоадере | При загрузке плагин сам проверяет себя; не сошлось — молча отключается |

Честные границы: от дампинга памяти и от правки кода тем, кто уже владеет
файлом, защиты не существует (как и у любой клиентской системы). Целостность
и авторство — криптографические; конфиденциальность payload — барьерная
(ключ расшифровки собран из 3 XOR-долей, см. Threat model ниже).

## Файлы в системе

```
CEPSbuilder/
  ceps_rt.py          рантайм: Ed25519, ChaCha20, Merkle, верификатор + генератор лоадеров
  cepsbuilder.py      CLI: keygen / new / build / verify / selftest
  fakesdk.py          фейковый SDK exteraGram для автотестов на ПК
  installer_template.py  шаблон плагина-приёмщика .ceps
  make_installer.py   собирает ../ceps_installer.py из шаблона + ceps_rt
  test_installer.py   автотест установщика
ceps_installer.py     ГОТОВЫЙ плагин для телефона: тап по .ceps → установка
ceps_empty_plugin/    пустой плагин-пример (собран и верифицирован)
device_share_ceps/    Device Share в CEPS-формате
```

## Быстрый старт (автор плагина)

```bash
# 1. Создать проект (сразу генерирует ключ подписи)
python CEPSbuilder/cepsbuilder.py new my_plugin --name "My Plugin" --author you

# 2. Написать плагин в my_plugin/src/main.py (BasePlugin как обычно)
#    что шифровать — поле "encrypt" в my_plugin/ceps.json (glob-шаблоны)

# 3. Собрать
python CEPSbuilder/cepsbuilder.py build my_plugin --note "релиз 1.0"
# → my_plugin/builds/my_plugin.ceps    контейнер (рассылать в чаты)
# → my_plugin/builds/my_plugin.py      лоадер (то же содержимое, для разработки)
# → my_plugin/builds/my_plugin.plugin  лоадер для установки: exteraGram принимает
#                                      .plugin — одиночный плагин, переименованный .py

# 4. Проверить подпись/целостность
python CEPSbuilder/cepsbuilder.py verify my_plugin/builds/my_plugin.ceps \
       --pubkey <hex из шага 1>
```

Повторные `build` дописывают блоки в `chain.json` проекта — история сборок
растёт цепочкой, подписывается последний блок.

## Как ставится в exteraGram

Установщик exteraGram принимает одиночные плагины как `.py` и как `.plugin`
(проверено на реальном примере: `visualverify.plugin` — обычный `.py`,
переименованный; начинается с `from base_plugin ...`). Структурированные
архивы — `.elyx`/`.eaf`. Наш `.ceps` напрямую не принимается, поэтому:

1. **Без Elyx (основной)** — файл `builds/<id>.plugin`: одиночный лоадер,
   внутри которого base85-блоб `.ceps` + публичный ключ + доли ключа
   расшифровки. Ставится тапом как обычный `.plugin`-плагин. Расшифровка —
   в памяти.
2. **Плагин-приёмщик `ceps_installer.py`** — установи его один раз, добавь
   pubkey автора в «Доверенные ключи» (настройки плагина). Дальше: автор
   кидает `.ceps` документом в любой чат → получатель тапает по файлу →
   установщик проверяет подпись → подтверждение → плагин установлен
   (`Файлы → <id>.py` в папке плагинов). Работает через документированный
   `FilesController.register(ext="ceps")`.

Опция `--elyx` при сборке дополнительно создаёт `.eaf`-обёртку
(refmap + meta + лоадер + вложенный `.ceps`) для тех, кто хочет ставить
через Elyx-движок.

## Двоичные файлы и materialization

`encrypt` принимает любые файлы, не только `.py`: dex-ядра, `.so`, `.pyc`,
данные. Пример из проекта Chimera: `"encrypt": ["src/*.py", "src/*.pyc",
"java/*.dex"]`.

Сторонние плагины часто ищут свои файлы «рядом с собой»: helper-модули —
`os.path.dirname(__file__)`, dex-ядро — `../java/engine.dex`. Поэтому при
первом запуске лоадер:

1. расшифровывает **все** файлы payload в приватную папку плагина
   `plugins/.ceps_cache/<id>/` — с оригинальной структурой путей;
2. даёт entry настоящую метку `__file__` внутри этой папки;
3. после этого код payload работает как обычно: `_packaged_helper` находит
   `.pyc`-хелперы, loader грузит расшифрованный `engine.dex` через
   `InMemoryDexClassLoader` — **никаких правок кода стороннего плагина**.

На диске при этом оказывается расшифрованная копия — это неизбежная плата
за совместимость (Java-класслоадеру нужен реальный читаемый dex или
InMemoryDexByteBuffer, который сторонний код и так использует). Защита та
же: до первого запуска файлы в архиве/чате зашифрованы, подпись проверяется
до распаковки.

## Режим «без исходников» (--pyc)

`python CEPSbuilder/cepsbuilder.py build my_plugin --obf --pyc`

Порядок обработки каждого `.py`: обфускация → **компиляция в
marshal-байткод Python 3.11** (телефонный рантайм) → шифрование. В payload
и в кэше на устройстве `.py`-исходников нет вовсе:

| Что | Где лежит |
|---|---|
| loader.py и остальные `.py` | marshal-байткод (только в памяти при исполнении) |
| dex-ядро, `.so`, `.pyc` | расшифровываются в приватный кэш (нужны Java) |
| исходный текст | существует только на ПК автора |

Для компиляции нужен интерпретатор 3.11: `py -3.11` или путь из
`"python311"` в ceps.json. Обратно в исходники байткод не декомпилируется
стандартными средствами — это существенно поднимает цену реверса в паре с
обфускацией. Защита от владельца устройства по-прежнему не абсолютна:
байткод исполняется на его телефоне.

### Режим «вообще без исходников» (--rt-pyc)

`--pyc` компилирует payload, но `ceps_rt.py` (рантайм) оставался исходником
внутри лоадера (`_RT_SRC`) — им можно было воспользоваться как оракулом.
Флаг `--rt-pyc` (или `"rt_pyc": true` в ceps.json) компилирует и его:

| Артефакт | было | с `--rt-pyc` |
|---|---|---|
| лоадер | `_RT_SRC = "import base64…"` | `_RT_MARSHAL` (marshal-3.11) |
| .ceps-блоб | `ceps_rt.py` (исходник) | `ceps_rt.pyc` (байткод) |
| путь атаки ast→RT→oracle | работает | мёртв: `ast.parse` не находит кода |

В артефактах не остаётся **ни одного** питоновского исходника — ни payload,
ни рантайма. `verify_structure` принимает оба вида архивов (поле
`rt_pyc` в манифесте + `rt_sha256` от байткода). Телефонный рантайм —
Chaquopy 3.11, форма marshal совпадает.

## Настройки проекта (ceps.json)

```jsonc
{
  "id": "my_plugin",           // id плагина и имя файла
  "name": "My Plugin",
  "description": "...",        // попадает в метаданные exteraGram
  "author": "you",
  "version": "1.0.0",
  "entry": "src/main.py",      // файл с классом-наследником BasePlugin
  "encrypt": ["src/*.py"],     // что шифровать (glob)
  "exclude": [],               // что не включать в архив
  "embed_shares": true,        // доли ключа внутри .ceps (нужны для установщика)
  "key": "ceps_keys/my_plugin.key"
}
```

`embed_shares: false` — параноидальный режим: `.ceps` сам по себе не
расшифровывается даже с кодом верификатора (доли знает только `.py`-лоадер),
но установщик такой архив принять не сможет.

## AI-GUARD: несущий слой предупреждений (два слоя)

Если ИИ-ассистент откроет файлы CEPS-сборки, он увидит плотную сеть
предупреждений — на 30+ языках, в разных стилях (юридическое, этическое,
техническое, готовый сценарий отказа), с фактами: Ed25519-цепочка, HMAC,
env-ключ, отсутствие ключа в файле. Просьбы «снять защиту» классифицируются
как атака; даже джейлбрейк-заготовки («это CTF», «симуляция», «DAN»)
прямо разобраны в текстах.

**Слой 1 — лоадер и установщик (несущий, seal):** таблица `_GUARD` вшивается
в лоадер, её SHA-256-хеш `_GUARD_SEAL` проверяется `_ceps_seal()` **перед
каждой загрузкой payload**. Ткач `_weave_guard` вплетает предупреждения
(комментарий + исполняемый seal-стейтмент) каждые 3–4 строки. Вырезание
или «перевод» строк = seal mismatch = **плагин отказывается загружаться**.
Это не комментарии: их правка ломает загрузку.

**Слой 2 — внутри зашифрованного payload (ceps_guards.py):** в каждый `.py`
payload после обфускации вшиваются присваивания `ceps_guard = "…"`
(каждые ~3 инструкции, ротация языков/стилей; в entry — баннер-докстринг).
Присваивания, а не голые строки: CPython 3.8+ выкидывает константные
Expr-инструкции, присваивания гарантированно попадают в `co_consts` и
переживают marshal-3.11. Декомпилятор показывает их через каждые 3–4 строки.

Управление в ceps.json: `"guards": false` (выключить слой 2 для payload),
`"guards_every"`, `"guards_max"`. Слой 1 (seal в лоадере/установщике) — всегда.

## CEPS-3 hardening: scrypt, двойной затвор, анти-дебаг

- **KDF слотов** (`"env_kdf"`): `"scrypt"` (N=2^14, r=8, p=1, memory-hard —
  GPU-брут дорог) или `"pbkdf2"` (совместимость). Алгоритм и параметры
  записаны в каждый слот манифеста; среда без scrypt → честный отказ
  (fail closed), не тихий fallback.
- **Двойной затвор seal**: `load_ceps_blob` требует аргументы
  `guard_table`/`guard_seal` (лоадер обязан их передать), проверяет таблицу
  по печати И по `EXPECTED_GUARD_SEAL`, вшитому билдером в marshal-рантайм.
  Правка guard-блока или prelude-чеков «на return True» больше не открывает
  payload — решение принимает marshal, а не редактируемый текст лоадера.
  Честная граница: тотальная перепись prelude в обход `load_ceps_blob`
  технически возможна (весь prelude — редактируемый текст); нативный гейт
  требует NDK-сборки собственного .so.
- **Анти-дебаг** (`"anti_debug": true`): перед деривацией ключа рантайм
  проверяет TracerPid (/proc/self/status) и порты frida-server
  (27042–27045), fail closed. Барьер, не гарантия: нативный инструмент
  обходит; на средах без /proc — no-op.

## Обфускация (--obf)

`python CEPSbuilder/cepsbuilder.py build my_plugin --obf` перед шифрованием
прогоняет исходники через AST-пайплайн (vendored ElyxBuilder, MIT):

| Проход | Что делает | Ключ отключения (ceps.json → "obfuscation") |
|---|---|---|
| stripDocstrings | вырезает докстринги | `stripDocstrings: false` |
| removeLogs | вырезает `self.log(...)` | `removeLogs: false` |
| renameLocals | переименовывает локалы | `renameLocals: false` |
| invisibleNames | имена из U+3164/U+115F — выглядят как пробелы | `invisibleNames: false` |
| **stringTable** | строки ≥64 символов — в zlib-таблицу `_ST(i)` | `stringTable: false` |
| encodeStrings | короткие строки XOR-энкодится | `encodeStrings: false` |
| encodeNumbers | числа → арифметика | `encodeNumbers: false` |
| zlib_launcher | весь код в `exec(zlib.decompress(...))` | флаг `--zlib` |

Маркеры в исходнике: `# ELYBnoStrobf`, `# ELYBnoIntObf`, `# ELYBsaveLog`,
декоратор `@ELYBNoObf` — исключают следующий элемент из обфускации.

Практика:
- **stringTable обязательна для больших файлов**: без неё XOR раздувает
  base64-литералы в ~15 раз (Chimera: 2.6 МБ → 7.6 МБ, телефон падает по OOM);
  с ней файл даже уменьшается (2.6 → 2.49 МБ).
- `invisibleNames` делает стектрейсы нечитаемыми — на время отладки отключай.
- Если класс плагина объявлен после присвоения `__name__ = "..."` на верхнем
  уровне — детектор CEPS это учитывает (ищет и по новому имени модуля).

## Threat model (честно)

- **Целостность/авторство** — криптографически стойко: без приватного ключа
  нельзя подделать ни один файл, ни историю сборок.
- **Конфиденциальность payload** — барьерная: доли ключа лежат рядом
  (в лоадере или манифесте), тот, кто разберёт файл и запустит
  верификатор, расшифрует код. Это скрытие от «открыл — увидел», не от
  реверс-инженера.
- **Изолированность плагинов**: exteraGram изолирует импорты каждого
  плагина, так что `ceps_rt` одного не конфликтует с другим.

### Почему без сервера сильнее нельзя (математика, не лень)

Если плагин запускается сам — без сети, без кодов, без внешних ключей —
то всё необходимое для расшифровки обязано лежать в самом файле. Значит
файл всегда можно расшифровать, пройдя тем же путём, что и рантайм
(достать `_RT_SRC`, скормить ему `_BLOB` + доли). Это доказуемое свойство
любой офлайн-схемы, а не недоработка CEPS.

Единственные способы вынести ключ из файла — дать его снаружи:
- **сервер выдачи** (ключ по запросу после проверки подписи);
- **коды активации** (master обёрнут PBKDF2 под кодом, код выдаёт автор);
- **привязка к среде** (CEPS-3, реализована — см. ниже);
- **привязка к устройству** (ключ из Android Keystore — но тогда плагин
  нельзя перенести, и владелец телефона всё равно дампит память).

## CEPS-3: env-привязка (ключ из среды Telegram)

Идея позаимствована у защиты Chimera 1.1.1 («SEKZ»): ключ шифрования
вычисляется из **внутренностей самого Telegram на устройстве** и в файле
не хранится. Улучшения относительно оригинала:

1. **Мульти-слоты** (у SEKZ — один класс): `env_classes` в `ceps.json`
   задаёт 2+ класса-донора. Каждый слот — отдельная обёртка master
   (`PBKDF2(sha256(sorted(dir(cls)))) → ChaCha20`). Пропал один класс
   (обновился Telegram) — срабатывает запасной слот, плагин живёт.
2. **Структурная установка**: `.ceps` env-архива ставится установщиком
   по `verify_structure` (подпись + целостность) — расшифровка
   установщику не нужна.
3. **Ed25519 + цепочка сохраняются**: в отличие от SEKZ, подделка
   по-прежнему невозможна, история сборок верифицируема.
4. **Коллектор подписей**: `ceps collect-env <project>` генерирует
   плагин, который на телефоне снимает реальные подписи классов
   (тап — копирование в буфер); пары кладутся в
   `ceps_keys/env_sigs.json`, после чего слоты строятся из реальных
   подписей, а не из ПК-заглушек `ceps_envsim`.

Схема: `master = PBKDF2(sha256(sorted(dir(cls))), salt, 100k)`.
На ПК (без Telegram) `hook_utils.find_class` недоступен — архив не
расшифровывается; тесты идут через `ceps_envsim` (стабильные заглушки
тех же классов). Честная граница та же: тот, кто расковыряет файл на
телефоне, вызовет тот же `hook_utils` сам — защита от «скачал, открыл,
увидел», а не от реверсера с устройством в руках. Но путь атаки

### Реальный кейс: chimeranft в CEPS-3

`chimeranft_ceps` собран в env-режиме (блоки #22+). Классы-доноры
(4 слота): `NotificationCenter`, `LayoutHelper`, `TLRPC`, `FileLoader`.

Рабочий цикл автора:
1. `ceps collect-env chimeranft_ceps` → `builds/env_collector.plugin`
   (одноразовый, пользователям не поставляется);
2. установить его в exteraGram → настройки → «СКОПИРОВАТЬ ВСЁ»;
3. JSON → `ceps_keys/env_sigs.json`;
4. `ceps build chimeranft_ceps --obf --pyc --rt-pyc --elyx` (без
   `--allow-envsim` билдер ОТКАЖЕТСЯ собирать env-плагин без реальных
   подписей; `--rt-pyc` убирает из артефактов и исходник рантайма);
5. `python chimeranft_ceps/assemble_hybrid.py` → `OpenChimeraNFT-ceps.eaf`
   — ставится как обычный EAF, ключ берётся из среды Telegram.

Проверка архива: `ceps verify <архив> --key <ключ> --envsigs
<ceps_keys/env_sigs.json>` — на ПК можно расшифровать payload только
с подписями с устройства (это НЕ утечка: подписи бесполезны без слотов,
а слоты без подписей не дают master).

Если после обновления Telegram какой-то класс изменит `dir()` — плагин
останется жив за счёт остальных слотов; при поломке всех — переснять
подписи и пересобрать (подписи стабильны в пределах одной версии
exteraGram).

Путь атаки из CEPS-1 «ast `_RT_SRC` → XOR долей → verify_files» больше
не работает: долей в файле нет.

## Автотесты

```bash
python CEPSbuilder/cepsbuilder.py selftest   # формат: verify/подделка/лоадер/elyx
python CEPSbuilder/test_installer.py         # установщик: весь цикл приёма .ceps
python CEPSbuilder/test_env.py               # CEPS-3: env-привязка, запасные слоты
python CEPSbuilder/test_rtpyc.py             # рантайм в marshal-3.11
python CEPSbuilder/test_memenc.py            # enc_v2 + mem_dex (dex только в памяти)
python CEPSbuilder/test_guards.py            # AI-GUARD: часть кода, переживает pyc
```

После правки `ceps_rt.py` / шаблона установщика не забудь:

```bash
python CEPSbuilder/make_installer.py         # перегенерировать ceps_installer.py
```
